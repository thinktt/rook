## Dedicated helper versus staged reuse

**Dedicated third helper, four total threads:** one owned Position publication,
one complete native map producer, a128B result installation and real retirement.
Then normal color dispatch still copies Position/map and runs both original side
chains. Count request/done/wakeup/reverse-edge traffic, waits, storage/startup,
between-search parking and an additional active-search spinning thread. There is
no removed FULL dispatch or second simultaneous map job. Mode1/default and
common ensure code must also price configuration/branch/layout changes.

**Existing color helper, three total threads:** that helper is available before
current FULL; prior calls have already joined before recursive search. A MapOnly
stage could do the same complete producer, retire it at ensure, then use the
normal actual-FULL request. This avoids the fourth thread, not Position/map
transfer or the extra stage. Today's two-reader Published flight cannot be reused
by declaring an inactive peer finished: real stage-specific acknowledgment or a
genuine separate one-reader lease is required. Output reuse and cold parking also
need the changed stage to be understood. That is intrusive protocol/common-path
cost, not an assumed free use of an idle reader.

Map-to-color continuation could publish Position and root-bound material/weights
early, retain the complete map, and authorize side arithmetic only after actual
FULL admission. If FAST's first gate rejects, FULL is known without consuming the map;
if the pressure/threat gate is attempted, its map-dependent decision comes later.
A FAST-only return must retire the map stage without any color arithmetic. The
peer still needs the map and authorization, and canonical scratch still needs
delivery. Such continuation changes publication/lifetime and is not a removed
dispatch in the simple staged option. It should not be silently combined with an
earlier-build discriminator or presented as rescue of fusion.

Schematically, with F the actual owner interval after publication, serial pays
`F + M`; remote pays `P + max(F, pickup + Mremote) + delivery/retirement` before
the unchanged decision/FULL suffix. Publication is a serial prefix. Certain demand
removes discard risk at the post-TT boundary; it does not make F large, remote
construction faster, delivery free or helper CPU invisible. The FAST-admitted-only
boundary is the cleanest narrower reserve, but its aggregate pool is unknown.
