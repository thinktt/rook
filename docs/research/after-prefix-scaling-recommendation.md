# Next scaling question after consumed-prefix recovery

2026-10-26. Recommendation from the closed paired evidence; no new implementation
or native run selected here.

**Prefer one actual2/4/8-worker internal-split discriminator over another
certificate change or tiny-prefix tuning. Do not scale the present root-tail
driver unchanged.** The paired test adds1,960 ahead nodes in35 but still yields
no surviving segment>=128 N. Its prefix executor proxy is17.500ms higher, including
9.550ms annotation; recovery itself adds7.950ms. The net removed-call proxy adds
about6.004ms, not the11.828ms gross newly maximal proxy, which includes previously
reused descendants. This implementation has no demonstrated favorable economics.

The result is specific to the **first naturally Restricted root iteration** and
its bounded tail forecast. Root aspiration windows and large preceding root
branches can alter requests, learning, TT and pawns before a queued task is used.
The two serial simulations are not tests of internal split readiness, later
iterations, recursive queue depth or real worker throughput. They also do not
establish that4/8 workers can amortize recording:35 records about224.6ms of ahead
speculation in the earlier single-policy pilot, before useful parallel overlap.

Internal ordinary parents offer a distinct boundary. The census observed
5,392/763/5,161 ordinary four-way boundaries with each branch>=128 N in35/08/43,
and3,464/259/1,701 eight-way boundaries. Those overlapping retrospective counts
are supply evidence, not ready tasks or saved-work budgets. In particular, they
do not prove that the first large child predicts large remaining children.

An internal split can begin **after child0 and any ensuing tail IIO complete**.
Initial IIO/quiet-mate work is already settled; no later parent reordering occurs.
At that point actual parent best, retained state, ordered suffix, extension flags
and first-child TT/learning/pawn effects are known. For a finite incoming window,
remaining full-window children have alpha fixed at `-request.upper`; their beta
is `-max(best,request.lower)`. A fail-low first child can keep that beta fixed
until a later improvement. This removes the root aspiration forecast, but later
children still mutate shared state and may invalidate speculative work. Existing
exact-input/native-effect validation and ordered fallback must remain.

The smallest actual queue test should activate at only **one prospectively
selected internal parent**, with selection based on known inputs and completed
child0 work, never future sibling timings. A concrete starting selector is a
proper finite window, remaining depth>=3, several remaining legal candidates,
and a substantial completed child0 (e.g.2,048 N). Freeze the selector before any
run and report a miss rather than retuning it. Wait through tail IIO. Let the
coordinator execute the next demanded child natively while1/3/7 workers prepare
bounded future sibling branches; use exact canonical demand to consume or discard
their results. No nested FULL helper or recursive queue is needed for this first
scaling question. The realized width, window changes, work sizes and waste decide
whether this boundary is useful.

One prerequisite is economically necessary: avoid a full16MiB TT copy per small
task. For this single batch, copy one immutable TT base and give workers native
group read-through/write overlays, with private pawn/learning snapshots. Share the
base across the batch; price its one copy and all per-worker initialization.
Reuse the existing native Group kernels and test overlay operations against flat
native state. Build worker-local Search/journals inside each thread so serial Rc
sinks do not cross threads; transfer explicit owned snapshot data and immutable
results. This is a bounded research backend, not a production TT-layout adoption.
Repeated internal splits would need a different snapshot strategy and are not
implied by this proposal.

Known lookup and recording costs argue against assuming a speedup, not against
measuring this different boundary. Closer snapshots and internal windows might
retain whole larger children and amortize those costs; they might instead expose
the same tiny recovery plus speculative CPU. Include one-thread native control,
actual2/4/8 wall and all-thread CPU, snapshot/record/replay costs, idle/startup,
memory and matched fidelity. Verify placement and disclose that8 workers share
all available guest cores with housekeeping. Keep independent oracle work outside
measured executor intervals; retain its existing transient-overwrite limitation.
No full qualification or PGO campaign is needed to answer this bounded question.

If internal splits also lose their coarse work, the concrete reserve is pure
result salvage from coarse speculative branch producers: retain placement/root-
epoch-bound Influence and Activity/Shelter results, consume them only inside the
original demand/charge boundaries, and leave canonical pawn selection and search
effects native. That differs from the parked depth2/first6 preparation policy,
but its actual cross-branch demand coverage and lookup/publication costs remain
unmeasured. Do not build that scheduler merely from position-match counts.
