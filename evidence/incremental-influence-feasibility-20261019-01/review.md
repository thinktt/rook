# Exact parent→child Influence: bounded feasibility

Exact derivation is algebraically possible for an actual two-square ordinary move or promotion, but current Search has no computed-map provenance capability. Position coherence alone is insufficient. The opportunity is conditional on an already demanded, privately computed parent map; eagerly constructing one would violate current Q demand. No implementation, selection, speed estimate or claim about workload eligibility follows.

**Numerical owner and affected set.** For each color/target, the byte is the sum of physical contribution weights modulo256 (influence.rs15–23,46–103,164–212). Thus child = parent − removed contributions + new contributions, using wrapping subtraction/addition, even after overflow. Saturating adjusted_relation243 is a different consumer rule and must never perform this physical removal. Decoding normalized bytes as an uncapped attacker census would be wrong (evaluation-relations.md15–24,117–122).

For source F→T, remove the mover’s complete old emission at F and any captured piece’s complete emission at T, then add the child mover’s complete emission at T. Promotion changes both kind and emission; a captured slider loses *all* its directions. Unchanged pawns/knights/kings have occupancy-independent targets and require no updates. Other changed emissions are only slider rays geometrically containing F or T, in either parent or child, with that slider’s allowed diagonal/orthogonal directions. Discover all collinear slider origins of both colors, not merely nearest legal attackers: own matching sliders/queens and opposing kings can be transparent. The conservative geometric set may include rays blocked earlier; exact recomputation can cancel those unchanged rays safely.

Deduplicate by unchanged origin/direction: F and T may select the same ray; one origin can have two affected directions. Exclude old/new F/T sources from the unchanged-source set to avoid double removal. A simpler complete-source replay can deduplicate origins and reuse current slider_masks, but recomputes unaffected directions too. A finer direction replay would need a shared extraction of the actual mask owner, not an independently copied formula.

Preserve first-occupied inclusion, own bishop/rook directional transparency, irreversible weakening beyond the first own queen, opposing-king transparency, own-king blocking, and the one-square forward-diagonal friendly-pawn extension even onto an occupied square (evaluation-relations.md46–80; influence.rs170–212; coherent.rs93–129). Different sources retain multiplicity; only a single source’s normal/weak masks are disjoint. Pawn/king moves can change many distant slider emissions. Turn, rights and EP flags do not themselves affect influence; source chronology remains required elsewhere although these sums commute.

Fresh43 uses one per-color invocation-local counter and one transpose only for colors with sliders (coherent.rs15–74,132–201). A differential design must compare complete setup/output/transport against that owner, including low-material/scalar paths; representation size alone proves no saving.

**Unforgeable provenance boundary.** Influence.profiles is public mutable data (influence.rs34–35). Both ensure routes accept arbitrary authoritative Some scratch and return it unchanged, including when geometry permission is true (evaluator.rs306–335). Engine’s bool validates Position only (engine.rs121–131). Existing Predecessor carries plain &Position/&Influence, not proof of their association (ordinary.rs512–517). Neither bool, map address, nor a matching placement hash certifies a supplied map.

A future private, ephemeral computed-map wrapper/capability must be constructed *only* at an actual native build/validated derivation, bind that exact unchanged parent placement and map, and remain unavailable through public/custom-map entries. Derivation may extend the capability only for an actual owned native child transition. Some supplied maps must remain untouched and must never mint that capability. Public full/select/observed signatures, synthetic profiles and stale public Position behavior stay on existing producers. Root, ordinary/IIO/scout/null/Q private edges would each need explicit provenance continuity; no token can be inferred from ordinary Predecessor alone. No Node/Position enlargement is necessary in principle, but extra argument/local lifetime and code/frame costs remain unproved.

**Demand and fallbacks.** Ordinary811–826 obtains its map before child work; IIO receives that map at1099–1106. Q267–283 can finish fast-only without a map, checked Q skips static selection, and destination support369–374 builds only inside its demanded closure. Child preparation408/443 precedes any child map demand. Therefore transport parent provenance optionally, but materialize a derived child map only at the child’s existing None→map event. Do not build maps for rejected/prefiltered children, reply probes, terminal-fast leaves or absent parent contexts. Preserve existing semantic R and materialization/observation stats boundaries, pawn retention, finishing, ordered effects and history/retry ownership.

A conservative boundary falls back fresh for custom/public inputs, missing provenance/map, EP’s three-cell transition (including admitted nonpawn victims), castling’s four cells, null transitions and checked paths without an established private context. Check does not mathematically invalidate the algebra; it does not establish provenance either. Promotion is two-cell but must remove pawn/add promoted emission. Null placement equality permits exact map reuse algebraically, yet changing its routing/demand is a separate obligation. Nothing requires broadening this scope.

Conclusion: mathematically exact; integration and economics unresolved. The smallest factual question is a privately authenticated, lazy bytewise parent-map delta with unchanged numerical mask owners and owned child state.
