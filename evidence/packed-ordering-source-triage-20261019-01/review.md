## Exact permutation, partition and API obligations

priority_sequence246–261 uses strict unsigned priority comparison, gap6 then gap1, moving each Move with its u32 priority. tactical-capture-order.md9–30 defines the resulting two-stage stable permutation, not a universal stable sort: residue classes retain their own tie order, then the combined sequence retains that modified tie order. For `[1,1,1,1,1,1,2]` the required indices are `[6,1,2,3,4,5,0]`. Equal-key whole records must not compare by Move/padding or any added tie-break. Preserve every16-bit Move payload unchanged and every full-u32 key, including0,1,u32MAX and values formed by earlier wrapping calculations.

order_by313–337 calls its FnMut priority callback exactly once for each original candidate, in original order. High keys>1 are written by decrementing first from capacity, thus reversing their original order; low0/1 Moves append at low in original order. Neither low0 nor low1 is sorted. After sorting ONLY scratch[first..], it outputs the preferred suffix followed by scratch[..low]. The invariant low+(capacity−first)=processed count prevents overlap for a valid len<=512. Packing must retain both partition regions and their occupancy invariant; do not sort/gather all physical slots, incorporate unused sentinels, reverse the low prefix, or confuse memory suffix with final preferred output prefix. search-candidate-order.md109–125 fixes these details and zero R for ordering; source admission, generation order, callback effects, N and later global learning/history stay outside the transport change.

Public priority_sequence's current parallel-slice API and behavior must stay intact. It does not assert equal lengths up front: zero/one Move may touch no priority element, a longer priority tail remains untouched, and a short priority slice may panic at a particular later indexed read after earlier mutations. Keeping its body unchanged avoids silently inventing validation/panic behavior. Current production order_by validates list.len through as_slice before callbacks and writes the caller's MoveList only after all callbacks and permutation. A callback panic leaves that list unpermuted while opaque workspace may be partially updated. New packing/gathering must preserve this boundary, not expose a partly rewritten list during callbacks.

## Complete cost and shared-kernel question

A whole-record shift may consolidate streams, but it transfers eight nominal bytes rather than the current six field bytes, and may need priority extraction for each comparison. All preferred records must first be formed; low payload handling remains. Current output uses two contiguous Move copy_from_slice operations335–336. Packed records interleave keys/padding, so final Moves need strided extraction/gather into the exact list prefix; raw byte-copying the packed region is wrong. That gather can replace efficient bulk transfers with scalar/vector unpack work. Capacity-preserving scratch grows1024B; an aligned u64 representation can also change alignment, while a field record's padding must never be read as an uninitialized integer through unsafe casting. No cache, traffic, spill or speed conclusion follows from nominal widths.

Parent retains the policy-ownership choice. Leaving public priority_sequence byte-exact and using a small private packed gap loop avoids public slice-admission changes but duplicates the policy and needs explicit drift controls. A statically shared loop could keep one policy, yet its adapters/inlining/access order must preserve public panic behavior and cannot silently allocate/pack an arbitrary public slice into fixed capacity. No generic adapter framework or implementation is proposed here. A later selected path would need direct tests of its actual packed consumer, because the unchanged public permutation test alone would still exercise the old parallel implementation. Existing independent modulo-six oracle and preferred/low tests are useful controls; full512, all-low/all-preferred, duplicate priorities, u32 extremes and mixed prefix/suffix occupancy matter.
