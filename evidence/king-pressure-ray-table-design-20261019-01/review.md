# Existing-table king-pressure traversal: feasible, already tried

Preliminary recommendation: do not select a new trial from this idea alone. It is exactly experiment32's valid-square mechanism, already parked after own-source PGO. Decision0023 records generic0.832364%lower, but own-PGO0.239039%higher/4of7lower and failed advancement. Current37 and prospective40 have different surrounding code; that can change economics, but is not concrete evidence to repeat the traversal. The substantive new requirement here is public invalid-source fallback, a semantic repair to the old proposal rather than an optimization mechanism. No prototype or candidate is selected by this review.

For a source<64, the concrete integration is small: retain the existing king list extraction, attacker/count acquisition and class gates; use ray directions4..8 with mask0xf0, then0..4 with0xcc. For each admitted direction iterate ATTACK_RAYS.0[source][direction].squares[..len] near-to-far. Exclude the first attacker-colored nonempty byte, include empty squares and the first defender occupant, then stop. For admitted knights iterate KNIGHT_SOURCES[source].squares[..len] in existing KNIGHT order, admit empty/defender occupied squares and mask3. Call the unchanged pressure_value at every admitted target; retain subtract12/clamp and original compute/mark/R ownership. No pressure-specific table, occupancy bitset, new cache or storage is needed.

The finite equality follows directly from geometry.rs35–57 and66–85: each ray was generated by the same Square::offset recurrence and DIRECTIONS order; each leap is the same ordered KNIGHT offset filtered by Option. Current activity.rs436–481 traverses orthogonal directions first, then diagonals; table construction's numeric storage order does not authorize reversing those consumer groups. Off-board padding must never be visited, no numeric-square sorting, no mask-mediated alias of an invalid origin. ATTACK_RAYS is4096B of fixed eight-byte Ray records; KNIGHT_SOURCES is64 Leaps of eight bytes plus length (source representation, not new measured footprint). Borrow records/slices; copying the entire source row or leap value is unnecessary.

This geometry is mailbox-independent and needs no trusted/coherent-position permission. Board bytes, public chronological king list, public opponent counts and arbitrary supplied marks retain their existing authority even when planes/lists/counts disagree. The consumer must keep byte is_empty/color admission, not use AttackBits, validate or reconstruct state. Counts decide whether a class is visited; actual board presence is not substituted. Released activity.md164–182 defines first-own inclusion/opponent exclusion and fresh mark presence. No moving-piece mobility transparency applies to king pressure. pressure_value may be arithmetic or the separately selected static lookup without changing this proof.

Invalid origin handling is consequential. Square(pub u8) admits values64..255; offset uses file=byte&7 and rank=byte>>3 and filters resulting coordinates. Square64 with south step(0,-1) reaches a8; invalid rank9 can re-enter via a knight -2 rank step. Therefore a table index panic or returning0 for every invalid origin changes behavior. After exactly the old piece_squares(...)[0] and count acquisition, branch source.0<64 to tables; otherwise retain the complete old scalar offset recurrence and original gates/calls. Do not mask source with63. Missing king or malformed count/list slices must still panic at their original extraction before this branch; do not introduce eager table access in a skipped class. The scalar fallback is also required when no class is admitted, where an invalid origin may still return0 without a table panic. Preserve malformed-board byte treatment, not just legal FENs.

The genuine proposed saving is repeated file/rank coordinate extraction, addition and edge tests. Required board admission and supplied mark reads/pressure arithmetic remain; table loads, source-row/address setup, direction length/end loops, bounds checks, loads of each target, fallback branch, code size and register pressure replace some of that work. Existing pressure32 own-PGO backend reportedly kept table traversal but grew activity175B and added8 static stack-reference instructions; that is a recorded old-artifact cost, not a current estimate. Old25 simulated envelopes and current40 generic gain cannot establish a current traversal opportunity or CPU benefit. The current40 own-PGO code already inlines pressure, so any future justification must inspect that exact final retained artifact and a distinct mechanism, rather than reuse old percentages or re-run32 by default.
