# Exact43 native owned-work/accounting audit

The known-single-process/single-thread premise is **supported for this exact ordinary native profile by its source**, conditional on the standard Rust/Linux runtime and controlled environment. I found no own-code route that creates a worker thread, subprocess, detached task, exec chain or asynchronous service. Direct-child wait4 is therefore a defensible whole-native-lifetime counter here. This is not a continuous descendant monitor, a platform proof, or new qualification of old receipts.

Panics abort rather than unwind in this release setting; the accounting method rejects nonzero/signalled samples. Standard I/O initialization/finalization, allocator, clock, loader/TLS and libstd/libc behavior remain imported implementation assumptions, not independently expanded source proof here. No source hook transfers finalization work to another owned worker.

Parent-side hashing, Node oracle/tap/controller work and Python waiting are separate processes outside that counter. Wall time includes waits/observation delays and is not CPU. Complete native wire formatting/seed/search ownership is in the native source, not implemented by the controller.

collect_games.py:124–145 requires strict completion, exact engine/argv/hash, normal direct exit, no supervisor interruption and disappearance of the recorded native/supervisor PIDs. Unexpected detached/unreaped subprocesses cannot be assumed covered by the direct-PID counter or that cleanup. No such source route exists in the inspected ordinary profile; adding one would invalidate this premise and require a different audit/accounting contract. Even if some operating-system counters aggregate more usage, this audit does not rely on them as arbitrary-descendant accounting.

**Remaining limits.** The two tools record selected injection/profile environment variables but do not themselves ban every preload/library/runtime alteration; applicability assumes the parent-approved artifact/environment closure, not any arbitrary invocation. The Rust compiler/stdlib, loader/libc and kernel accounting implementation were not audited or scanned during this live window. Absence of own spawn calls is strong bounded evidence, not formal absence of any platform-created worker. One early task snapshot cannot exclude a short-lived later worker, and the parent's9b60af/0 four-process/fourteen-task observation is only a point corroboration. No claim of continuous single-thread execution, exclusive host ownership, all asynchronous kernel CPU attribution, or descendant-complete monitoring follows. These limits already fit the reported-only source premise; no concrete omitted own worker was found and no old receipt is relabelled.
