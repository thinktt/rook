## What a correct move delta entails

Native placement changes are in `position.rs:269–345`: ordinary/capture and promotion affect source plus destination; EP additionally removes the behind-target occupant; castling also relocates the rook (four cells). Promotion changes contribution category. Joined EP must use the actual removed occupant, including admitted nonpawn victims; the separate cold king-victim continuation removes that king before normal application (`position.rs:251–265`). No pawn-only or standard-ancestry assumption is valid for that component domain. Null affects zero placement cells. A changed occupied square can change type/color/transparency even when its occupancy bit remains set.

Pawn, knight and king source contributions depend only on source/type/color geometry. Their moved, promoted or removed source contributions can be replaced locally. Unmoved slider contributions depend on the board along each traced ray. A conservative repair would identify all potentially affected old/new slider sources or rays through changed cells, remove each affected old contribution exactly once, and add each new contribution exactly once. Changed sources themselves require removal/addition of their complete applicable rays. Deduplication matters when multiple changed cells intersect one source/ray. A geometric superset is safe but discovering it and rescanning sources can cost substantial work; no small affected-set bound follows from two/four changed cells.

The current ray owner (`influence.rs:159–201`) includes an occupied target before deciding continuation. Enemy kings are transparent; own kings block. Compatible friendly rook/bishop chains are transparent. A friendly queen weakens every later contribution on that ray, without later restoration. A friendly pawn on a forward diagonal adds one final square even if that extra square is occupied. Consequently nearest-blocker/legal-attack invalidation is insufficient: several sliders behind transparent pieces may be affected, and changes can propagate beyond the first piece. Both old and new placement dependencies matter. Full-source repair is easier to specify than a minimal suffix patch; suffix repair would need the incoming weakened weight and prior stopping state, not merely a blocker square.

The mixed-radix normalization is exactly modulo256 weighted accumulation. Exact physical old-ray/source removal therefore uses wrapping subtraction, followed by wrapping addition of the new physical contribution. It does not require retaining discarded high carries. `adjusted_relation` instead saturates a subtraction *after normalization* for a semantic query; using that exclusion as an update operator is incorrect. Preserve all 128 bytes, not just classified relations or capped multiplicities: central balance and support consume distinctions hidden by relation categories. Numerical accumulation commutes, so map contribution iteration order may differ; Position's chronological lists, native pawn-cache order and all consumer visitation/query order must remain unchanged.

## Preliminary alternatives and proof obligations

1. **Lazy null borrow:** carry a reference to the already valid parent map and use it only at the child's existing first map demand. This avoids a map payload copy in the abstract design; it still adds parameter/control/lifetime obligations. It must propagate through ordinary-to-Q handoff and preserve default caller ABI deliberately, rather than assume a compiler erases the transport. Null's full evaluation, retained age/reset, pawn-cache access and actual relation queries still run normally when admitted.
2. **Lazy parent/transition hint:** ordinary already has parent position/map/movement; derive a child map only at existing ensure demand. Missing Q hints fall back to current construction. This avoids eager repair for children that return before a map is needed. A child result still needs writable 128-byte storage unless using a more elaborate view. Repair plus copy and dependency discovery can exceed a fresh build. Q needs an explicit optional ownership path, and retained retry reuse is separate scope.
3. **Persistent map or reversible scratch:** adding a map to every Node/Position copies/stores 128 payload bytes on paths that currently need none and enlarges existing aggregate/frame/capture costs. Side storage introduces validity/index/unwind rules. In-place update/unmake conflicts with live parent-map comparisons and sibling/retry/stop lifetimes unless original data or deltas are preserved. Maintaining through each `set_square` would also traverse temporary transition states, where lists/board are not yet jointly final; it must not inspect stale ownership or expose a partial map. These are broader alternatives, not a recommended first implementation.

Any later prototype should share the actual ray semantics rather than duplicate a second policy and prove full-profile equality against fresh construction over both colors, transparent chains/weakening, wrapping, occupied extra squares, promotions/captures/castles and broad EP continuations. Null must compare equal despite side/rights/EP/counter differences. End-to-end proof must keep full/fast refresh points, retained P/G/age and nonking-square ownership, exact cache hit/miss/zero/collision history, candidate ordering, checked/reply/history/child chronology, interruption boundaries and all R charges. Construction/reuse must never suppress or memoize repeated semantic relation queries. The `influence_builds` diagnostic counter describes current construction and would need an explicit instrumentation policy if mechanisms change; it is not evidence of measured work saved.

Before architecture selection, establish from the later authorized evidence how often maps are demanded after ordinary/null/Q transitions and the distribution of affected sources/rays, then examine emitted copy/ABI/frame/spill and default-path effects and matched CPU cost. This review has collected none of those counts. Keeping current invocation-local scratch is a valid outcome if transport costs or maintenance risk dominate.
