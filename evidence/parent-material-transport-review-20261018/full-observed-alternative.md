# Existing FULL scalar export alternative

Additional small source read: current src/evaluator.rs310-322 and433-453. `full` and `full_observed<F:FnOnce(Components)>` invoke the same nonfresh `full_impl::<false>`; the only component-observer argument differs. There is no dynamic trait object or allocation in the source API. `Components.material` is the exact root.material result computed at363, not derived from a score. The callback occurs at446 AFTER retained updates and R accumulation, BEFORE base/single finish. Capturing that scalar into a caller local would require no additional native material call or public Evaluation field, and should retain that actual callback/order.

A focused provider-only alternative could begin with already unavoidable root preparation FULL and ordinary FULL (all ordinary recursive child creation is after FULL). Those owners can retain the existing material via this static callback and supply a current-node hint only to count-preserving children. A pre-FULL ordinary FAST cutoff has no descendants to seed; a failed FAST cutoff proceeds to FULL anyway, so lack of FAST export need not block this narrower parent-provider slice. It must not be counted as FAST->FULL within-invocation reuse.

This is not a complete mechanism by itself. Consumers still need a shared native demanded-material input seam to avoid their own RootContext::material calls. Root preparation must hand its captured scalar to the actual root controller/Predecessor owner. Q's FAST-only selected parents cannot seed a new hint through the existing FastDetails (which exposes base/Finished, not material); they must remain unknown unless they inherited a valid scalar. Checked Q likewise creates none. Captures/promotions/EP still invalidate, so a FULL-provider-only slice can be narrower than a full per-demand propagation scheme. Count that difference rather than eagerly recomputing material or inferring it from a finished score.

The source API is statically dispatched but lowering is NOT known free: its callback receives a Components aggregate by value; a capturing closure can affect inlining, live aggregate copies, scalar spills, recursive frames, full_impl monomorphs or call transfers. Existing ordinary full uses a zero-sized no-op, so replacing it changes a production instantiation even if Evaluation/Node sizes are unchanged. The current compiler may eliminate unused component copies and inline a scalar extraction; only emitted default caller/body evidence can establish that. Do not route ordinary search through large FullDetails observers merely to claim a convenient scalar if a smaller shared seam is chosen later.

Decision remains contingent. The planned post12 exact-current profile35/08 attribution should first establish meaningful current material cost; old8d2.51% simulated profile01 attribution is not current own-PGO share. If material is already cheap, extra hint classification/transport can outweigh many source-demand hits, and no new cache/census/prototype need follow. If profile share warrants it, the proposed demand-only census can distinguish full-provider inherited hits, missing FAST-only providers, zero-demand edges and local-repeat overlap before selecting a representation. No codegen/counter/native execution or implementation is selected by this addendum.
