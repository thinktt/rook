## Exact controls and pass scope

LLVM19.1.7 [CodeLayout.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.7/llvm/lib/Transforms/Utils/CodeLayout.cpp#L53-L61) sets `enable-ext-tsp-block-placement` false and `ext-tsp-apply-without-profile` true. Enabling only the first therefore also affects functions lacking profile data, using their available estimates; a profile-only proposal would additionally set the second false. That is a prospective scope choice, not a tuning result.

[MachineBlockPlacement.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.7/llvm/lib/CodeGen/MachineBlockPlacement.cpp#L3267-L3278) applies ExtTSP only with at least3 machine blocks and the enabled/profile gates. It runs after chain/tail-merge work and before branch optimization/alignment. Its input uses machine block frequencies, estimated instruction sizes and edge probabilities (3319–3363). Thus PGO improves its available information but does not bypass the enable gate. This is a late intra-function placement heuristic, not whole-function linker reordering or guaranteed identical instruction encodings. Reordering may change fallthroughs/branches/padding and final code size; do not promise unchanged frames, calls or machine bytes without a real later artifact review.

Rust1.85.1 [llvm_util.rs:44–138](https://github.com/rust-lang/rust/blob/1.85.1/compiler/rustc_codegen_llvm/src/llvm_util.rs#L44-L138) forwards user LLVM arguments and adds no ExtTSP enable here. The saved version-matched write.rs, PassWrapper.cpp and LLVM X86TargetMachine.cpp contain no ExtTSP reference. This is bounded source evidence against an automatic Rust/x86 PGO override, not a claim to have run the compiler pass pipeline. [Rustc's codegen reference](https://doc.rust-lang.org/rustc/codegen-options/index.html#llvm-args) documents the LLVM-argument interface; these backend-specific switches are not a stable portable Rust optimization contract.

A prospective rustc argv value is `-C llvm-args=-enable-ext-tsp-block-placement=true`. In a PGO-use recipe preserve the existing warning too; one argv value can be `llvm-args=-pgo-warn-missing-function -enable-ext-tsp-block-placement=true`. If root deliberately chooses profile-only scope, add `-ext-tsp-apply-without-profile=false` inside that same value. Freeze that choice before any build/result; no parameter sweep is proposed. Keep target-cpu=x86-64, O3, thinLTO,1CGU, panic=abort and every semantic/FP/ISA setting unchanged. ExtTSP itself requests placement, not fast-math, unsupported ISA or altered engine algorithms. Backend correctness and actual whole-program behavior still need validation; a flag name cannot prove equivalence.
